## 1. SvelteKit 的 full-stack 能力：已经有，别加后端

SvelteKit 不是"前端框架 + 需要另配后端"，它本身就是全栈框架。本站已经用满：

| 能力 | 本站用法 | 文件 |
|---|---|---|
| 服务端渲染 | 每个页面的 `load` 直接读库 | `src/routes/**/+page.server.ts` |
| 服务端 API | 51 个 REST 端点 | `src/routes/api/**/+server.ts` |
| 服务端表单 | 后台管理页的 action（无需手写 fetch） | `src/routes/admin/library/+page.server.ts` 的 `actions` |
| 请求中间件 | 全局鉴权、缓存头、活动记录 | `src/hooks.server.ts` |
| 数据库直连 | `node:sqlite` 同步 API，零第三方驱动 | `src/lib/server/db.ts` |
| 构建产物 | 单进程 Node 服务 | `@sveltejs/adapter-node` |

**结论：不需要引入任何后端框架。** 需要的是把这套能力**用得更规整**（第 8 节的 API 结构），以及在部署层补上环境隔离与备份（第 3、5 节）。

唯一要注意的边界：SvelteKit 的 `+server.ts` 是**每个端点一个文件**，没有统一的路由分组/中间件链概念。所以"统一鉴权"只能靠 `hooks.server.ts` + 各处调用 `currentUser()`/`getApiUser()`。这就是为什么本仓库会出现"每个路由自己写一遍 `verifyToken`"的重复——已经有 `src/lib/server/session.ts` 做收口，新接口一律走它。

## 2. WAL 与"日志级回滚"：一半已达标，一半是概念错位

### 2.1 WAL 已经开了

`src/lib/server/db.ts:470-473`：

```ts
db.exec("PRAGMA journal_mode = WAL;");   // 读写并发
db.exec("PRAGMA foreign_keys = ON;");    // 外键约束
db.exec("PRAGMA busy_timeout = 5000;");  // 锁等待 5s，规避偶发 SQLITE_BUSY
```

这套配置对**单机 SQLite + 多读少写**的场景是标准解，无需改动。

### 2.2 但 WAL **不等于**"可回滚到任意历史点"

这是需要纠正的一个概念。WAL 保证的是**崩溃一致性**：断电/进程被杀后，数据库不会停在"改了一半"的状态，重启会自动前滚或回滚未提交事务。它**不提供**：

- 回滚到"昨天 15:00 的数据"
- 撤销某个用户今天误删的一批数据
- 跨表/跨业务的统一版本历史

如果你要的是这些，需要的是另外三样东西，而它们**部分已经有了**：

| 需求 | 手段 | 本站现状 |
|---|---|---|
| 改了什么、谁改的 | 审计表 | ✅ 已有 `console_audit`，且带 `prev_hash/row_hash` 哈希链（防直连改库） |
| 恢复到某个时间点 | 定期快照 + 保留策略 | ❌ **缺**（第 3 节要建的） |
| 单条记录的历史版本 | 版本表 / 事件溯源 | ❌ 缺，且**不建议全表引入**（成本极高，只在个别表按需加） |

**建议的边界**：不要追求"所有业务表都能任意回滚"。成本收益比很差，而且会拖慢每一次写入。正确组合是：

1. **审计**（谁改了什么）→ 已有哈希链，覆盖管理操作；
2. **快照**（恢复到某个时间点）→ 第 3 节，日/周/月三级；
3. **软删除**（误删可救）→ 对高价值表（`users`、`attachments`、内容表）加 `deleted_at`，删除只标记不真删。

第 3 条是"日志级回滚"里**最实用、最便宜**的一环，建议优先于做版本表。

## 3. 数据库备份：加密 + 定时 + 多方异地

### 3.1 现状与缺口

| 项 | 现状 | 缺口 |
|---|---|---|
| `/api/backup` | 手动触发，导出 `posts/projects/docs` 的 JSON | **不含 SQLite 数据**（用户/会话/附件元数据全都不在内） |
| 加密 | 可选 AES-256-GCM，口令由请求头传 | 无固定密钥、无自动加密 |
| 定时 | 无 | 全靠人记得点 |
| 异地 | 无 | 只有本机磁盘 |
| `content/` 文件 | 无备份 | `nav.json` / `changelog.json` / `roadmap.json` / `docs/*.md` / `archive/posts/*` 全在这 |

**关键结构问题**：本站的数据是**分裂**的——结构化数据在 SQLite（`content/stelarith.db`），文件型数据在 `content/` 目录（JSON/MD）。备份必须**同时覆盖两者**，否则恢复出一个"有用户没有内容"或"有内容没有用户"的残站。

### 3.2 铁律：WAL 模式下禁止直接复制 .db 文件

必须写进脚本注释，否则后人一定会踩：

> SQLite 处于 WAL 模式时，数据可能只落在 `stelarith.db-wal` 里还没合并进主库。
> 直接 `cp stelarith.db backup.db` 拿到的**不是**一个完整快照——
> 它可能是"主库旧状态 + wal 里新事务"被拆散的一半，恢复时静默丢数据。
>
> 正确做法：`VACUUM INTO '<目标路径>'`。
> 它在**事务内**读取、生成一个**独立、已整理、单文件**的完整副本，
> 全程不会阻塞读、不会让运行中的服务感受到锁。
> 且 SQLite 3.27+ 原生支持，`node:sqlite` 直接 `db.exec()` 即可，无需第三方库。

### 3.3 借用的原则：3-2-1

备份界有一条几十年的老规矩，几乎能回答所有"我到底该怎么备份"的问题：

> **3-2-1 原则** —— 至少 **3** 份副本，放在 **2** 种不同介质上，其中 **1** 份在异地。

| 要求 | 本方案对应 | 满足 |
|---|---|---|
| 3 份副本 | 本机 + R2 + 异地三方 | ✅ |
| 2 种以上介质 / 存储类型 | 本机磁盘（块存储）+ 对象存储 | ✅ |
| ≥1 份异地 | 份 3 ＝ **Backblaze B2**（不同服务商、不同凭证） | ✅ |

它还能纠正一个常见误解：**"云备份" ≠ "异地备份"**。
如果生产库和备份在同一台机器上，那"本机一份 + 同一块硬盘上的另一份"只算 **1 份** ——
介质没换、位置没换，一次磁盘故障全丢。放上 R2 才算第二份，因为它们终于不在同一块盘上了。

### 3.4 备份链路（建议实现）

```
[每 03:00 计划任务]
   │
   ├─① 一致性快照   VACUUM INTO content/backups/staging/<ts>.db
   │
   ├─② 打包文件     content/ 里的 JSON / MD（排除 staging 自身、排除 *.db-wal）
   │
   ├─③ 加密         AES-256-GCM，密钥取 .env 的 BACKUP_KEY（32 字节 base64）
   │                文件头写明 alg / iv / tag，便于十年后还原
   │
   ├─④ 校验         回读密文 + 重新解密 + 打开 SQLite 跑 integrity_check
   │                ★ 校验失败就**不推进保留策略**，宁可堆旧备份也不删
   │
   └─⑤ 分发三方
        ├─ 份 1 本机   content/backups/local/     （防误删，不防机器坏）
        ├─ 份 2 R2     backups/sqlite/YYYY/MM/    （跨区，复用现有 r2.ts putObject）
        └─ 份 3 B2     <bucket>/sqlite/YYYY/MM/   （Backblaze B2：独立账号、独立凭证）
```

**保留策略（GFS 三代）**：日 7 份 / 周 4 份 / 月 12 份。超出部分才删，且**只删本机份**，R2 上永久保留到人工清理——云存储便宜，误删不可逆。

**份 3 已选定 Backblaze B2。** 当时的三个候选与取舍（留档，避免以后重复权衡）：

| 方案 | 成本 | 优点 | 缺点 |
|---|---|---|---|
| Backblaze B2 | 约 $6/TB/月，10GB 内基本免费 | S3 兼容，`r2.ts` 改个 endpoint 就能用 | 需再开一个账号 + 密钥 |
| 另一台机器（同校/家里 NAS） | 0 | 完全自控 | 需对方可达（rsync/scp） |
| GitHub 私有仓库 | 0 | 有版本历史，天然异地 | 仓库体积上限建议 <1GB，需定期清理；**不适合存加密大备份**，只适合存配置/文本内容 |

> ⚠️ 份 1 和份 2 是**同一台机器发起的**，防不了"密钥泄漏导致云备份被一并删除"。真正的异地要求份 3 用**不同的凭证、不同的服务商**。这是"多方"的含义。

### 3.5 一条不能省的纪律：没演练过的备份不算备份

脚本必须同时提供一个 `--restore <文件> --to <临时目录>` 模式：解出快照 → 起一个临时 SQLite → `PRAGMA integrity_check` → 打印关键表行数（users / sessions / attachments / activities）。

**每月至少手动跑一次恢复演练**，并把结果记进本目录的日志。理由很直接：加密脚本里写错一个 iv 长度、打包时漏了 `-wal` 文件，平时完全看不出来，等到真出事才发现备份是废的——那比没有备份更令人绝望。

### 3.6 密钥管理

`.env` 新增（**不入库、不进 git**）：

```
BACKUP_KEY=<32 字节 base64>          # openssl rand -base64 32 生成
BACKUP_R2_PREFIX=backups/sqlite/     # 复用现有 R2_* 五项配置
BACKUP_KEEP_DAILY=7
BACKUP_KEEP_WEEKLY=4
BACKUP_KEEP_MONTHLY=12
```

> **`BACKUP_KEY` 丢了 = 所有备份都解不开。** 必须离线抄一份（纸质/密码管理器），
> 且**不能**和 R2 的密钥放在同一个地方——否则一起丢或一起泄。

### 3.7 落地状态（2026-09-26）：已实现，份 3 待填凭据

脚本 `scripts/backup-db.mjs` 已实现并端到端实测通过（含模拟 S3 端对 R2 / B2 双路上传的验证）。
入口：`scripts/backup.bat`，npm 别名 `npm run backup`。

```
npm run backup                   完整备份
npm run backup:plan              只打印将要做什么，不落任何数据
npm run backup:verify <file>     校验一份密文能否解出、SQLite 是否完整
npm run backup:restore <file>    恢复演练（默认写临时目录，绝不覆盖生产）
```

**实测结论**：VACUUM INTO 快照 → AES-256-GCM 加密 → 回读校验（HEAD 比字节数 + 解密自验比 sha256
+ 起临时 SQLite 跑 `integrity_check`）→ 三方分发 → GFS 轮转，全链路通过。
一次备份约 0.8s、33 MiB（其中数据库 712 KiB，其余是 content 与 uploads 的明文副本）。

**纪律生效的证据**：当前 `.env` 里 B2_* 一项未填，脚本在本机份落盘后**直接在中止退出**，
输出「B2 未配置…… 现在只有本机 + 无两份」。它不会为了"能传几份传几份"而返回成功。

**尚未完成的三件事**（需要人工）：

1. **填 B2 凭据**——只有换了服务商才算异地。缺了它，整套备份实际上只防误删、不防机器坏。
2. **装计划任务**——`scripts\backup.bat --install-task`（需管理员），之后每月确认一次它真的跑过。
3. **每月一次恢复演练**——`npm run backup:restore <本机份里的 .db.enc>`，把结果记进本目录。
   没演练过的备份不算备份；这条纪律的价值要到真出事那天才体现，而那时候已经没机会补练了。

### 3.8 实现过程中抓到的 5 个真 bug（都已在代码里留了注释）

备份代码里隐藏的 bug 极其安静——不报错、不崩溃，只是悄悄把数据弄丢或弄多。这一轮的实测抓到 5 个：

| # | 现象 | 根因 |
|---|---|---|
| 1 | 密钥恒读为空，报"未配置 BACKUP_KEY"（误导） | `.env` 载入写在 `CFG` **求值之后**，顺序反了 |
| 2 | 解密自验报 `Unexpected non-whitespace after JSON` | 容器头偏移写成 12，实际 meta 起于 11（magic 7 + 长度 4） |
| 3 | 轮转把历史快照全当陌生目录 | 时间戳 `20260926T…` 与解析正则要求的 `2026-09-26T…` 不匹配 |
| 4 | 保留判定永远不命中 | keepSet 存目录名，判定却拿日历日字符串去比 |
| 5 | **每次备份都会把上一次备份再备份一遍** | `walk()` 顶层文件没带 `content/` 前缀，SKIP 规则全部失效 |

第 5 个最危险：文件数从 95 一路涨到 99、103……直到磁盘被自己的备份塞满，
而在那之前日志上只显示一句「分发 N 个文件」，看上去完全正常。

### 3.9 顺带发现：生产当前没有配置 R2_*

`.env` 里 R2 五项一项未填，也就是说站点附件目前走的是 `r2.ts` 的**本地磁盘回退**分支——
文件落在 `uploads/` 而不是对象存储。后果有两条：

- 备份**(已包含** `uploads/`），所以附件没有被漏掉；
- 但一旦需要多实例或需要"换台机器把站整体搬走"，本地盘就是不可迁移的单点。

建议下一步补上 R2（详见第 2 节的取舍），那是与备份互相独立的一件事。

## 4. Cloudflare 域名优选：有这功能，但本站现阶段不建议上

### 4.1 功能确实存在

它叫 **Cloudflare for SaaS**（控制台入口：SSL/TLS → 自定义主机名 / Custom Hostnames）。原理是：

```
访客 → CNAME 到「优选域名」（CF 优选 IP）→ CF 边缘节点
     → CF 按 Host 识别出你的域名（Custom Hostname 映射）
     → 回源到你的真实服务器（Fallback Origin）
```

好处：域名**不必托管在 CF**，也能享受 CF 的代理、证书、优选线路；服务器真实 IP 被藏在 CF 后面。

### 4.2 但本站有 3 条硬约束，先看清楚

| 约束 | 具体 | 对本站的影响 |
|---|---|---|
| **① 单请求体上限 100MB** | CF 免费版（含 Pro）代理的上传请求体上限 100MB | ⚠️ **直接冲突**：本站附件上传上限是 `MAX_FILE_BYTES = 200MB`。上了 CF 代理，超过 100MB 的上传会被边缘直接拒掉，而站内代码完全无从感知 |
| **② 回源可达性** | CF 必须能主动连到你的源站 | 本机若在校园网/家用宽带（无固定公网 IP 或端口被封），必须先有 Tunnel 或端口映射。这与"Vercel 保守接入"是同一类约束 |
| **③ 优选域名不属于你** | 优选域名是第三方维护的（如 `cdn.xxx.xyz`） | 上游下线你就得改解析；且这类用法在 CF ToS 上一直是灰色地带。开通 Custom Hostnames 还**必须绑定支付方式** |

### 4.3 判断：优先做 R2 静态化，而不是优选

本站访客以同校/同区域为主，延迟需求是真的。但**当前延迟瓶颈不在"选哪个 CF 边缘节点"，而在本机出口带宽**——所有 HTML 都在本机 8090 渲染并吐出去，CF 边缘再优选也绕不开这段回源链路。

正确顺序：

1. **先做静态资源与附件的 CDN 化**（`/_app/immutable/*`、`/uploads/*`、R2 上的图片）→ 这些占带宽的大头，挪到 R2/CF 后本机回源压力骤降；
2. **再评估优选** → 那时回源只剩动态 HTML，优选才有意义；
3. 如果真要上，**必须同时**把 `MAX_FILE_BYTES` 降到 100MB 以下，或改成"客户端直传 R2（预签名 URL）"——后者更好，因为大文件根本不经过本站（顺带省掉本机的内存峰值）。

**结论：优选可以做，但排在 R2 静态化之后。顺序反了就是白折腾。** 第 4.2 节的 ① 是必须先在代码里解决的硬冲突。

## 5. 热更新与环境：真话 + 可落地的三档方案

### 5.1 真话：生产不可能有 HMR（而且不该有）

| | 开发 | 生产 |
|---|---|---|
| 启动方式 | `vite dev` | `node build/index.js` |
| 改代码后 | **HMR，秒级生效，不刷新** | **必须重新 build + 重启，约 1 分钟** |
| 产物 | 内存中即时编译 | 预构建的静态 `build/` |

你写的 "HMR X" 说的是**生产**。生产没有 HMR，而且是**结构性的**——要"生产热更新"，等价于"在生产跑 vite dev"，那正是你自己列为禁止项的东西（它没有优化、内存占用高、崩溃即全站停）。

**但你真正想要的不是 HMR**，是这两件事：

1. 改完能**立刻看到效果**，且**不影响线上用户**；
2. 上线时**不要有"构建中打不开"的窗口**。

这两件事都能做到，而且第 2 件**已经做到了 70%**。

### 5.2 已经做到的：旁路构建 + 原子切换

`scripts/release-site.mjs` 已经实现了"构建不碰线上"：

```
node scripts/release-site.mjs build    → 构到 build.next，全程不碰正在服务的 build/
node scripts/release-site.mjs switch   → 停服窗口内两次改名完成切换，验收失败自动回滚
```

配套的 `svelte.config.js` 支持 `STELLARITH_BUILD_OUT` 覆盖输出目录；`site-crash-guard.cjs` 兜住"构建时恰好有人请求旧文件名"导致的整进程崩溃（历史上因此连崩 22/24 次 = 每次 3~4 分钟全灭）。

**还差的两块**：切换时仍有几秒停服；构建本身受本机内存限制（14GB 物理内存，V8 堆要限）。补上"预热"就是完整蓝绿（见 5.5）。

### 5.3 你的目标态需要修正一处

你写的是：

```
生产  www.245959623.xyz/admin      → 200  (prod/v1)
开发  localhost:8090/admin?M=v2    → 200  (dev/v2)
```

`?M=v2` 这个设计**在 SvelteKit 里做不到**，原因很硬：

> adapter-node 的产物是**预构建**的。一个 Node 进程启动时加载**一套** SSR manifest / 一套 `_app/immutable` 资源表。
> 想在同一进程里按 `?M=v2` 切到另一套构建，等于要自己实现"多构建产物共存 + 动态加载 + 双份 hydration 状态隔离"——
> 那是在**自研框架**，投入产出比极差，而且会引入一堆只有自己遇到的 bug。

**替代方案更好也更简单**：用**端口或域名**区分，而不是 query 参数。

- 本地：`localhost:8090`（prod 产物）vs `localhost:8091`（dev）—— 一眼分清，浏览器能同时开；
- 线上：`www.245959623.xyz`（prod）vs `v2.245959623.xyz`（preview）—— 反代按 Host 分流到两个进程。

### 5.4 环境隔离：当前最大的实际问题

现在：`dev-clean.bat` 和 `run-prod.bat` **都用 8090**，**都读同一个 `.env`**，**都写同一个 `content/stelarith.db`**。

后果：
- 开发时改了 schema，生产库跟着变；
- 开发时误删数据，生产数据真没了；
- 想在线上跑 dev 调试，必须先杀掉生产（"在生产环境开发"就是这么发生的）。

**改法（成本最低、收益最大）**：

| 维度 | prod | dev | preview |
|---|---|---|---|
| 环境标识 `STELARITH_ENV` | `prod` | `dev` | `preview` |
| **数据根** `STELARITH_DATA_ROOT` | `.`（缺省 = 工程根） | `.dev-data` | `.preview-data` |
| → 内容目录 | `content/` | `.dev-data/content/` | `.preview-data/content/` |
| → 上传目录 | `uploads/` | `.dev-data/uploads/` | `.preview-data/uploads/` |
| 数据库**文件名** | `stelarith.db` | `stelarith.db` | `stelarith.db` |
| 配置文件 | `.env`（缺省） | `.env.dev` | `.env.preview` |
| 端口 | 8090 | 8091 | 8092 |
| 启动 | `run-prod.bat` | `run-dev.bat` | `release-site.mjs` |
| 产物 | `build/` | 内存（vite HMR） | `build.next/` |

两处刻意设计，都不是笔误：

**① "数据库文件名"三格完全相同。** 这是单一变量原则（5.6 原则③）的直接后果 ——
环境差异应当由**数据根**这一个维度承载，其余名字一律恒定。
一旦让文件名也跟着变（`stelarith.db` / `preview.db`），你就得到了三个需要各自记住的名字、
三条要各自维护的路径，以及一个必然会漏改的地方。

**② 数据根一个变量管 `content/` 与 `uploads/` 两个目录。**
本仓库的这两个目录是**平级**的顶层目录。如果只外置 `content/`，
那 `uploads/` 就成了唯一还写死在工程根下的运行时数据 —— 这正是"半搬状态"：
库换了、上传目录没换，于是开发时上传的图片会直接落进生产的图床目录，而且是静默的。

**③ 缺省即生产。** 不配 `STELARITH_DATA_ROOT` 时数据根就是工程根，
`content/` 与 `uploads/` 维持历史位置 —— **既有部署与计划任务一行都不用改**（原则②：缺省态不写出来）。


#### 落地记录：以为是"改一处"，实际是"收口 11 处"（2026-09-26）

原方案写的是"需要一处代码改动：`db.ts` 的 `DB_FILE` 改成读环境变量"。**这个判断是错的。**
实际扫下来，`path.resolve("content")` / `path.resolve("uploads")` 散在 **11 个模块**里：

| 模块 | 原本各自写死的路径 |
|---|---|
| `db.ts` | `content/stelarith.db`、`content/users.json` |
| `content-store.ts` | `content/**` + `uploads/**` |
| `changelog.ts` | `content/changelog.json` |
| `project-board.ts` | `content/project-boards.json` |
| `rss.ts` | `content/cache/` |
| `oauth-clients.ts` | `content/oauth-clients.json` |
| `console-ext.ts` | `content/captures` |
| `file-transfer.ts` | `content/files` |
| `api/project-board/upload`、`…/download`、`routes/uploads/[filename]` | `uploads/` |
| `storage/r2.ts` | `uploads/`（未配 R2 时的本地回退） |

这就是"环境隔离做不干净"的根源：**改一个环境变量要记得改 11 个地方，漏一处那部分数据就静默写进生产目录。**

所以正确的顺序是**先收口、再外置**，不能直接加变量：

1. 新建 `src/lib/server/paths.ts` —— 全工程**唯一**允许出现 `"content"` / `"uploads"` 字面量的地方；
2. 11 处全部改为 import 它；
3. 然后才引入 `STELARITH_DATA_ROOT`。

`paths.ts` 刻意只收"根与顶层目录"，不收各模块私有的子路径。理由：
隔离所需的最小充分集就是这一个根；其余子目录由模块自己 `path.join(CONTENT_DIR, …)` 拼，
只要 `CONTENT_DIR` 唯一，它们就自动跟着走。把每个文件名都登记进来，只会让这个文件长成
"所有路径大全"，反而没人愿意维护 —— **收口的价值在"根唯一"，不在"清单完整"。**

**验证**（直读 `paths.ts`，两种情形）：

| 情形 | CONTENT_DIR | UPLOADS_DIR |
|---|---|---|
| 不配 `STELARITH_DATA_ROOT` | `<工程根>\content` | `<工程根>\uploads` |
| 配 `STELARITH_DATA_ROOT=.dev-data` | `<工程根>\.dev-data\content` | `<工程根>\.dev-data\uploads` |

第一行与历史路径**逐字符一致** —— 这是"既有部署零变更"的实测证据，不是承诺。

> 附带修掉一处**注释与实现长期矛盾**：`storage/r2.ts` 的文件头写着
> "配置缺失时**不**静默降级到本地磁盘"，而实现从第 243 行起一直在降级、且不打任何日志。
> 现在的写法是诚实的：配齐 R2 走对象存储；一个都没配则回退本地 `uploads/`，
> **并在首次回退时打一行 warn**；配了一半（缺字段）则抛 `StorageNotConfiguredError` 不猜。
> 让降级可见，比禁止降级更实际 —— 静默才是一切"存哪了"玄学的源头。

> **借用的约束（12-Factor App · Factor X：Dev/prod parity）**
>
> 环境隔离**只允许隔离配置，不允许隔离技术栈**。dev 与 prod 必须跑**同一份代码、同一个 adapter、同一种数据库引擎**，
> 差别只在端口、数据目录、密钥、以及是否走 HMR。
>
> 这条是对上表的**边界约束**，防止隔离过头。一旦 dev 为了"方便"换成别的数据库，
> 那么只在 prod 才会暴露的问题（SQLite 的并发行为、WAL 的实际表现、SQL 方言差异）就一个都测不出来 ——
> "隔离"反而让问题更容易漏到线上。12-Factor 的原话是 dev/prod 差异过大会让 "it works on my machine" 永久化。
>
> 换句话说：**dev 的价值恰恰在于它足够像 prod。**

### 5.5 三档路线（按需推进，不必一次做完）

| 档 | 内容 | 成本 | 解决什么 |
|---|---|---|---|
| **L1 环境隔离** | dev 独立端口 + 独立数据库 + `.env.dev` | 半天 | "在生产环境开发、污染生产" |
| **L2 预热式零停机** | `release-site.mjs` 补一步：新版本先起在 8199 自检（首页/API/DB 全通）→ 通过才切 → 切换后 30s 内保留旧进程兜底 | 1 天 | 切换时的几秒停服；上线等待 |

### 5.6 命名规范：原则，而不是对照表

我第一版给的是一张对照表（环境/槽位/构建三层 + 四条禁令）。**但对照表有个根本毛病：它只能覆盖你想到的情况。**

证据就是它自己：同一节里我写出了 `stelarith.db` / `dev/stelarith.db` / `dev/preview.db` 三种写法——
三层规范管的是"环境名"，管不到"文件名"这一层，于是三行就飘了。

所以这里改成给**原则**：让名字可以**被推导**，而不是被记住。

#### 五条原则（按优先级）

**① 一个维度只用一种表达。** 同一个"环境"维度会出现在端口、目录、文件名、脚本名、配置名五处——五处必须能用**同一条规则**生成。

**② 缺省态不写出来。** `prod` 是缺省，所以是 `.env` 而不是 `.env.prod`，是 `content/` 而不是 `content/prod/`。
这条还有个实际好处：**既有部署路径一个都不用动**。

**③ 单一变量：环境差异只体现在一个维度上，其余名字恒定。**
违反案例（我第一版）：`content/dev/preview.db` —— 既换了目录层级，又换了文件名。改一个维度动了两个地方。
正确形态见 5.4 的表：**文件名三格相同，只有目录变。**

**④ 名字表达"是什么"，不表达"做什么"。**
违反案例：`dev-clean.bat`。"clean" 是它做的事，不是它的身份——从这个名字**推导不出** prod 版该叫什么，于是团队里就会出现第三种叫法（现在确实有：`start-website.ps1`）。

**⑤ 外部约定优先于内部规范。**
`PORT` / `HOST` / `ORIGIN` / `COOKIE_SECURE` 是 adapter-node 的保留变量，**改名即失效**。规范要服从它们，不是反过来。

#### 三层名字（不许混用）

| 层 | 取值 | 用在哪 | **禁止** |
|---|---|---|---|
| **环境** `environment` | `prod` \| `dev` \| `preview` | 端口、数据目录、`.env.<env>`、启动脚本名 | ❌ 用 `v1`/`v2` 当环境名 |
| **槽位** `slot` | `a` \| `b` | 蓝绿切换的进程/目录后缀 | ❌ 用槽位名当环境 |
| **构建** `build` | `<yyyymmdd-HHmm>-<git短哈希>` | `BUILD_ID`、`/api/version`、页面脚注 | ❌ 固定值 `v0.0.1` |

**四条硬禁令**（写进 CONTRIBUTING）：

1. ❌ 生产环境跑 `vite dev`。
2. ❌ 开发环境跑 `node build/index.js`（那是验证生产产物时才用，用完即停）。
3. ❌ 把版本号当环境名：`prod/v1`、`dev/v2`、`dev/v3` 这种一律禁止。**版本是构建的属性，不是环境的属性。**
4. ❌ 一次启动出现多个环境标识。启动时打一行日志：`[boot] env=prod slot=a build=20260926-1738-3f9a1c port=8090 db=content/stelarith.db`。

现状对照：`svelte.config.js` 的 `BUILD_ID` 缺省是 `v` + `package.json` version = `v0.0.1`，**是个固定值**。这满足"client/server 一致"的硬要求，但无法区分两次发布。建议构建时由 CI/脚本注入时间戳+哈希，缺省回落到 `v0.0.1` 保持兼容。

另外，`/api/version` 现在返回的是**桌面端 OTA 的版本**（`xingjikong` 安装包版本），**不是站点自身版本**。语义容易混，建议：
- 桌面端 OTA 保持 `/api/version`（老客户端在用，不能动）
- 站点自身版本新增 `/api/v1/meta/build`，返回 `{ env, slot, build, startedAt, commit }`

#### 5.6.2 A 级问题的完整因果（作为"命名如何造成 bug"的标本）

```svelte
<!-- 修改前：src/routes/admin/oauth/+page.svelte:209 -->
{#if !process.env.PUBLIC_SITE_URL}
	<span>（未配置 PUBLIC_SITE_URL，取的是当前访问地址）</span>
{/if}
```

客户端产物里，它被编译成了：

```js
a(He, e => { ({}).PUBLIC_SITE_URL || e(Ue) })
```

`process.env` 被 SvelteKit **静默替换成空对象字面量 `({})`** —— 不报错、不告警，永远返回 `undefined`。于是：

| | 服务端（SSR） | 客户端（hydration） |
|---|---|---|
| `process.env.PUBLIC_SITE_URL` | 有值（`.env` 里配了） | `({}).PUBLIC_SITE_URL` = `undefined` |
| `!…` | `false` | `true` |
| 结果 | 不渲染 | **渲染** |

两个后果：**① hydration 不一致**；**② 运维在页面上看到一条与事实相反的提示**——
明明配了，却告诉你没配。

**根因是命名**：`PUBLIC_` 前缀在 SvelteKit 里**有特殊语义**（会经 `$env/static/public` 注入客户端）。
这个名字暗示"前端可以用"，于是有人就在 `.svelte` 里直接用了——而正确的通道是 `$env/*/public`，不是 `process.env`。

**修法**：由 `+page.server.ts` 的 `load` 把结果算好传给页面（`baseSource: "site-url" | "origin" | "request"`），
`.svelte` 只读 `data.*`。顺带修正了判据——原条件只看 `PUBLIC_SITE_URL`，
但 `ORIGIN` 在生产是 `run-prod.bat` 显式设置的，所以**只有两者都没配**才该警告。

> **已固化为静态门禁**：`scripts/check-svelte-client-env.mjs`，2026-09-26 接入 `ci.yml` 的
> `static-gates` job（**阻断级**，失败即让 workflow 变红）。
>
> 规则：**任何 `.svelte` 里出现 `process.env` 都是 bug**（注释行除外，文档里提到不算违规）。
> 全工程扫描确认当前只有这一处，已修。
>
> 门禁自测过双向：干净状态 `exit 0`；植入一处违规后 `exit 1` 并准确报出文件与行号。
> —— 门禁本身必须能被测试，否则它只是一段没人验证过的正则。
> （同 `site-crash-guard.cjs` 用 `STELARITH_CRASHGUARD_LOG` 让护栏可测是同一个考虑。）

### 5.7 关于 "CI/CD 太慢"

现状：CI（`.github/workflows/ci.yml`）**只做校验，不发版**；发布是本机跑 `release-site.mjs`。所以"上线等待"≈ 本机构建时间（受 14GB 内存限制，V8 要限堆）。

三个杠杆，按收益排序：

1. **构建与切换分离**（已在做）→ 构建期间站点照常服务，用户零感知；
2. **预热**（L2）→ 消除切换的几秒停服；
3. **增量构建/缓存** → 收益有限，因为 SvelteKit 的 client/server 两次构建都要重跑，且 `_app/immutable` 内容哈希一变就是大量新文件。**不建议**为此引入复杂缓存，容易得不偿失。

**结论：CI/CD 的"慢"不在 CI，在本机构建与内存。真正的解法是让"构建"完全不影响"在线服务"，这一点已经做到了。** 剩下的优化空间主要在 L2 的预热。

### 5.8 事故记录：构建在服务运行时进行 → 全站 500（2026-09-26 19:57）

本节是 5.2 节（旁路构建）和 5.7 节（CI/CD）的**实证**。记在这里，是因为同类事故本仓库已经发生过两次，
每次都靠人临场诊断，而根因始终是同一句话。

**现象**

`http://127.0.0.1:8090/` 返回 `{"message":"Internal Error"}`，`stelarith.out.log`：

```
[500] GET /
Error [ERR_MODULE_NOT_FOUND]: Cannot find module
  '...\build\server\chunks\0-C8UDiosz.js'
  imported from '...\build\server\chunks\manifest.js-q1p7D2Me.js'
```

**机制（四步）**

1. 19:54:45 生产进程启动，加载当时的 `build/server/chunks/*`，把 manifest 的 import 图**缓存在内存**；
2. 19:57:36 `build/` 被一次**普通 `vite build`**（未走 `STELARITH_BUILD_OUT` 旁路）整体重建，
   `server/chunks` 与 `client/_app/immutable` 的文件名都带内容哈希 —— 旧 chunk `0-C8UDiosz.js` 随之从磁盘消失；
3. 运行中的进程仍持有旧 import 图，一旦要懒加载那个 chunk → `ERR_MODULE_NOT_FOUND`。
   而 `site-crash-guard.cjs` 的豁免名单只覆盖 `ENOENT under build/client` 与 socket 中断，
   **不含** `ERR_MODULE_NOT_FOUND`，于是护栏按原行为放行退出；
4. 启动器 10s 退避重拉 —— 但此刻 `build/` 可能仍在被写，于是又崩。实测 19:57–20:01 连续 4 次退出（`RC=-1`）。

**对照证据**：该进程此前自 09-24 18:20 起**连续稳定运行约两天**，重启全部集中在 19:54 之后 —— 即构建发生的时间窗。

**这正是 `release-site.mjs` 存在的理由。** 它的 `build` 把新版本构到 `build.next`，全程不碰正在服务的 `build/`；
`switch` 才在停服窗口内做两次改名。**绕过它直接 `vite build`，等于把这个已经被解决过一次的问题重新引入。**

**顺带暴露一个守护逻辑盲区（已记录，未修改）**

`run-prod.bat` 的 `:healthcheck` 判据是：

> 只有"端口被占但完全没有 HTTP 应答"才算 STUCK；**5xx 仍证明进程活着，不该 kill**。

这个取舍在多数场景下正确（避免误杀活跃进程）。但在"产物被替换导致全站 500"这类场景里，
它会让故障变成**永久性的**：进程非常健康地返回 500，守护认为它健康，于是没有任何机制来重启它。

**建议（未实施）**：给健康检查加"连续 N 次（如 3 次）5xx 亦判定为异常"，或把 5xx 与"完全无应答"分开计数。
改动 `run-prod.bat` 属高风险动作，应与部署流程一并验证，不单独变更。

**教训**：构建与运行**必须**隔离到不同目录。这不是洁癖 ——
它是**唯一**能结构性避免这类事故的手段，靠纪律（"记得别在生产构建"）迟早会失效。

## 6. 会话体系：本站没有"多套 JWT 状态不同步"的问题

### 6.1 本站用的是服务端会话，不是 JWT

`src/lib/server/auth.ts:308-309, 463`：

```ts
const token = crypto.randomBytes(32).toString("base64url");   // 不透明随机串
// 落 sessions 表，verifyToken() 每次查库 JOIN users
```

对比：

| | JWT（你担心的那种） | 本站做法 |
|---|---|---|
| 载荷 | 自包含，签名可离线验 | 只是一个随机 ID |
| 状态 | **分散在各业务**，各自签发 | **集中在 `sessions` 表** |
| 吊销 | 做不到（只能等过期或维护黑名单） | **删一行立即下线** |
| 多业务不一致 | ✅ 会发生（这就是你描述的痛点） | 不会——所有业务查同一张表 |
| 代价 | 无状态查询快 | 每请求一次 DB 查询（单机 SQLite 可忽略） |

**结论：这个问题本站天然不存在。** 反而 JWT 才是会带来"状态不同步"的那一方。

### 6.2 现有多个 token 是"不同信任域"，不是重复建设

| token | 用途 | 真源 | 要不要合并 |
|---|---|---|---|
| `admin_token` | 主站会话 | `sessions` 表 | 基准 |
| `verify_token` | 邮箱验证（一次性） | `users` 表 | ❌ 用途不同，生命周期只有几分钟 |
| CIMS 会话令牌 | 代理到 CIMS 后端 | CIMS 自己 | ❌ 外部系统，不是我们的身份 |
| p2p 设备令牌 | 设备间互信 | HMAC-SHA256 派生 | ❌ 信任域不同（设备 ≠ 用户） |
| OAuth 授权码 | 第三方"用本站账号登录" | `oauth_clients` + 库 | ❌ 标准协议，形态固定 |

这些**不该合并**——强行合并会破坏各自的信任边界。要做的是**文档化**（新增 `docs/身份与令牌总表.md`），把"身份真源唯一（`users` 表）"这条铁律写死，避免以后有人再加一套。

## 7. API 路由整理

### 7.1 现状问题

51 个 `+server.ts`，四类毛病：

| 问题 | 例子 |
|---|---|
| 动词/名词/代词混用 | `/api/auth`（动词）、`/api/me`（代词）、`/api/users`（名词） |
| 单复数不一致 | `users`（复）vs `library`（单）vs `stats`（复） |
| 无版本前缀 | 将来 breaking change 无处安放 |
| 平面堆叠 | `nav` `pages` `posts` `docs` `search` `settings` `stats` 全在第一层 |

### 7.2 目标结构（按业务域分组）

```
/api/v1/
  identity/   auth/login  auth/logout  auth/register  auth/verify
              me  me/password  oauth/*
  content/    posts  pages  docs  nav  announcements
  community/  forum/channels  forum/threads  comments  activities  presence
  storage/    library  library/folder  library/[id]  library/[id]/compress  backup
  console/    cims/*  sign-task  ext/*
  admin/      users  users/titles  permissions  settings  oauth-clients
              admin/library  admin/library/purge
  meta/       health  version  build  stats  search  feed-config
```

### 7.3 落地方式：重写层，不搬目录

**不要在文件系统里搬目录。** SvelteKit 的路由就是目录结构，搬了会产生 51 个文件的 diff，还得同步改所有客户端调用点（桌面端、ClassIsland 插件、面板），且极易漏。

**正确做法**：在 `src/hooks.server.ts` 里加一层**路径重写**：

```
入站 /api/v1/identity/auth/login
   → 内部 rewrite 为 /api/auth
   → 老路径 /api/auth 继续可用，但响应带 Deprecation 头
```

好处：
- 对外统一到新命名，**内部实现零改动**；
- 老调用方**不断线**（桌面端 OTA、插件、面板不用同步发版）；
- 老路径打 `Deprecation: true` + `Sunset: <日期>`，观测一段时间（看日志里还有谁在调），确认无人使用后再决定是否真搬文件。

新写的接口一律用 `/api/v1/...` 命名。

> 注意 SvelteKit 的实现细节：需要在 `handle` 里构造 `new Request(新 URL, 原 request)` 再交给 `resolve`，
> 且**不能**只改 `event.url`（它是只读的）。同时要保留原 URL 供鉴权/日志用（放进 `event.locals`）。

## 附：一句话回答每个原始问题

1. **SvelteKit 有没有 full-stack** — 有，而且是本站的地基，不用换栈。
2. **WAL** — 已开（`db.ts:471`）。但要区分"崩溃一致性"（已有）和"可回滚到历史点"（要建快照 + 软删除）。
3. **备份加密多方异地** — 缺，方案见第 3 节。铁律两条：WAL 下用 `VACUUM INTO` 不用 cp；没演练过的备份不算备份。
4. **Cloudflare 域名优选** — 有（Cloudflare for SaaS），但 100MB 上传上限与本站 200MB 冲突，且收益被本机回源瓶颈吃掉。排到 R2 静态化之后。
5. **热更新** — 生产不可能有 HMR（那是"生产跑 vite dev"，禁止项）。要做的是环境隔离 + 零停机发布，见第 5 节。
6. **多套 JWT** — 本站不存在，用的是服务端会话表，比 JWT 更能即时吊销。
7. **命名** — 立三层规范：环境 `prod/dev/preview`、槽位 `a/b`、构建 `时间戳-哈希`。四条硬禁令见 5.6。
8. **`api/*` 整理** — 目标结构见 7.2，落地用重写层（不搬目录），老路径不断线。

## 附二：本方案借用的外部原则（不自己发明轮子）

| 原则 | 出处 | 用在哪 | 它约束了什么 |
|---|---|---|---|
| **3-2-1 备份** | 备份工程惯例（数十年） | 3.3 备份链路 | 副本数、介质数、异地数；并纠正"云备份 ≠ 异地备份" |
| **GFS 保留策略**（祖父-父-子） | 传统备份轮转 | 3.4 保留策略 | 日 7 / 周 4 / 月 12，避免"备份把磁盘塞满" |
| **WAL + busy_timeout** | SQLite 官方推荐的单机并发配置 | 2.1 | 无需引入数据库服务进程 |
| **`VACUUM INTO` 做快照** | SQLite 官方（3.27+） | 3.2 | 禁止在 WAL 下 `cp` 文件 |
| **12-Factor · Factor III（Config）** | 12factor.net | 5.4 环境隔离 | 配置进环境变量，不进代码 |
| **12-Factor · Factor X（Dev/prod parity）** | 12factor.net | 5.4 边界约束 | **隔离配置，不隔离技术栈** |
| **单一变量 / 正交性** | 通用设计原则 | 5.6 命名原则③ | 改一个维度只动一处 |
| **one-way door / two-way door** | AWS 决策框架 | 5.6.1 审计分级 | 决定"哪些不一致值得回溯改名" |
| **Blue-green / Canary** | 部署惯例 | 5.5 L2/L3 | 零停机切换、小流量验证 |
| **服务端会话 > JWT（本场景）** | 会话管理惯例 | 6.1 | 可即时吊销；避免多业务各签一套 |

> 用法说明：这些原则是**用来否决方案的**，不是用来装饰文档的。
> 比如 12-Factor 的 parity 就否掉了"dev 换 Postgres 图方便"这种做法；
> one-way door 就否掉了"把 22 张表全部改名求整齐"这种做法。
> 一条原则如果不能否决点什么，它就没有被真正用上。
