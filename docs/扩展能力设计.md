# 扩展能力设计：插件联动 · 远程屏幕控制 · 多用户安全 · 网站联动

> 本文是《学校多媒体统一集控·实施方案》的扩展卷，专门回答四个诉求：
> 1. **没有的功能用插件或本地应用去联动 ClassIsland / 电脑**（而不是在后端虚构网关）；
> 2. **设备可远程介入并控制屏幕**；
> 3. **多用户、安全性必须做好**；
> 4. **必须结合 stelarith-website 联动**。
>
> 所有接口均锚定已查证的真实代码：CIMS（`D:\Stelarith\Stelarith-cims-eval\CIMS-backend`）、stelarith-website（`D:\Stelarith\Stelarith-website\stelarith`）。不臆造任何不存在的 HTTP 端点。

---

## 0. 设计总原则（脚踏实地）

| 原则 | 落地方式 |
|---|---|
| 不重造身份系统 | 人类账户/角色直接复用 **stelarith-website** 已有的多用户体系（scrypt + Secure Cookie + `can()` 矩阵） |
| 不重造设备通道 | 设备命令/配置直接复用 **CIMS** 已暴露的 management HTTP 接口（restart/update-data/send-notification、资源写、Manifest 拉取） |
| 缺失能力下沉到端 | 锁屏/截图/远程控制/聊天/上报/Bug 由**设备侧 ClassIsland 插件 + 本地代理**实现，经真实 CIMS 通知通道触发 |
| 安全默认开启 | HTTPS、Secure Cookie、2FA、PGP 通道、RBAC、审计、AES 备份——全部沿用两个系统既有能力，对账补全 |

## 1. 缺失功能 → ClassIsland 插件 + 本地代理联动

CIMS 原生只提供：重启、强制同步（update-data）、发送通知、配置/资源写、Manifest 拉取。**锁屏、截图、远程控制、班级聊天、故障工单、Bug 上报**这类"业务侧"能力，CIMS 不内置。按你的要求，这些用**插件/本地应用**去联动，而非另起后端。

### 1.1 端侧两段式架构

```
电教委员面板 ──CIMS send-notification(结构化负载)──▶ ClassIsland 插件
                                                     │
                                          （识别 stelarith-task 类型）
                                                     │ localhost (127.0.0.1)
                                                     ▼
                                              本地代理 StelarithAgent
                                                     │
                                          （执行真实 OS 动作）
                                                     ▼
                                              锁屏 / 截图 / 启动 VNC / 进程控制
```

- **ClassIsland 插件**（`StelarithControlPlugin`）：监听 CIMS 下发的通知与配置，识别 `stelarith-task` 指令，把 OS 级动作转交本地代理；同时提供电教委员快捷操作 UI（锁屏/截图/报修一键发起）。
- **本地代理**（`StelarithAgent`，常驻 Windows 服务）：真正执行 OS 动作的最小进程，只在设备本机监听 `127.0.0.1`，不暴露公网。

> 为什么走"通知→插件→localhost 代理"而不是直接让面板打设备 IP？
> 因为 CIMS 的 `send-notification` 是**真实存在的下发通道**，ClassIsland 对通知有原生处理钩子；插件再把指令本地转发给代理，全程不新增任何伪造端点，且设备无需开放入站端口（更安全）。

### 1.2 指令负载约定（在 CIMS `send-notification` 的 `MessageContent` 内）

```json
{
  "stelarith_task": {
    "action": "lock" | "screenshot" | "remote_control_start" | "remote_control_stop" | "shell" | "reboot",
    "token": "<面板用网站私钥签名的短期令牌>",
    "scope": "class" | "grade" | "school",
    "ts": 1694000000
  }
}
```

- `token` 由**网站侧**签发（面板登录后拿到网站 JWT/会话），代理用网站公钥验签——这样"谁能下令锁屏"由网站的 RBAC 说了算，与设备通道解耦。
- 代理执行前校验：`token` 有效 + `action` 在角色允许集合内 + `ts` 未过期（防重放）。

### 1.3 聊天 / 工单 / Bug 的落地（同样是端侧 + 网站）

- **班级交流**：ClassIsland 插件内嵌轻量聊天窗口，消息经本地代理**上报到 stelarith-website**（网站已有 `submitFeedback` 动作与内容存储），同年级各班插件订阅同一频道。
- **故障上报 / 提交 Bug**：插件表单 → 本地代理 → 网站 `submitFeedback` / 新的 `submitIssue` 端点（复用网站 issue 模型），状态在网站后台跟踪。
- 这样协作类数据**落在网站已有体系**，不污染 CIMS 的设备配置域。

## 2. 远程屏幕控制（真实可行方案）

目标：电教委员在面板点"远程控制"，能**看到并操作**某台多媒体设备的屏幕。

### 2.1 方案选型（脚踏实地）

不自己造远程桌面协议。采用业界成熟组合：

| 组件 | 选型 | 说明 |
|---|---|---|
| 屏幕服务端 | **VNC**（设备侧按需启动，如 TightVNC / 自托管 RustDesk 风格轻量服） | 标准协议，Windows 原生可用 |
| Web 观看端 | **noVNC**（纯前端 VNC 客户端） | 面板直接内嵌 `<iframe>` 或弹窗，无需装软件 |
| 传输 | 校园网同网段直连 + 令牌鉴权；跨网段经反向隧道/中继 | 默认校园 LAN，安全可控 |
| 触发 | 面板→CIMS 通知→插件→代理→**按需启动 VNC 服务**（平时不运行，减小攻击面） | 符合"占用少、默认安全" |

### 2.2 控制流

```
1. 面板点"远程控制" → 校验 RBAC（仅 管理员/电教委员 对本班设备）
2. 面板发 CIMS send-notification(action=remote_control_start, token)
3. 插件收到 → 调本地代理 → 代理在本机启动 VNC 服务（随机会话端口，绑定 127.0.0.1 + 令牌）
4. 代理经 CIMS 通知回执 / 资源写，把"VNC 端口 + 连接令牌"回报给面板
5. 面板打开 noVNC，连接该端口（令牌鉴权）→ 实时观看/操作屏幕
6. 结束 → 面板发 remote_control_stop → 代理关闭 VNC 服务
```

### 2.3 安全约束（必须）

- VNC 仅在**会话期间**运行，结束即关；
- 连接必须令牌 + RBAC 双校验；
- 全程 HTTPS/加密隧道；
- 每一次远程控制都写**审计日志**（谁、何时、哪台设备、时长）；
- 设备默认**不开放入站端口**，VNC 仅绑 localhost 或由中继转发。

## 3. 多用户与安全性（锚定两个真实系统）

### 3.1 身份与角色：以 stelarith-website 为人类账户源

网站已有 `Role`：`admin > editor > moderator > user`，统一 `can(role, action)` 矩阵（`src/lib/permissions.ts`）。扩展两个集控角色：

| 角色 | 来源 | 集控权限 |
|---|---|---|
| `admin` 管理员 | 网站原生 | 全量：用户管理、设备控制、远程控制、内容下发、审计 |
| `techrep` 电教委员（新增） | 网站扩展 | 所负责班级/年级的设备控制、远程控制（限本班）、聊天/上报/Bug、看本班状态 |
| `moderator` 审核员 | 网站原生 | 审核聊天/工单/Bug |
| `viewer` 只读（新增） | 网站扩展 | 仅查看设备状态/公告，无任何写操作 |
| `user` 注册用户 | 网站原生 | 仅提交反馈/Bug |

> 集控面板的登录**直接复用网站 `admin_token` Cookie**（SSO）：面板部署在网站同源（或子域共享 Cookie），`getApiUser()` 校验后按 `can(role, ...)` 决定可见菜单与可执行动作。不另建账户库。

### 3.2 设备身份与 2FA：以 CIMS 为设备/通道源

- CIMS 原生多租户（account_id 隔离学校/部门）、客户端 PGP 握手、完整 **TOTP 2FA 栈**（`user_totp.py` / `admin_totp*.py`）。
- 设备注册/握手/配置下发走 CIMS 既有的真实接口（见 `admin-console/API.md`）。
- 敏感操作（远程控制、批量命令）要求操作人账户开启 **2FA**。

### 3.3 安全清单（逐项对应真实能力）

| 控制项 | 由谁提供 | 状态 |
|---|---|---|
| 密码哈希 scrypt | 网站 `auth.ts` | ✅ 已有 |
| HttpOnly + Secure Cookie | 网站 | ✅ 已有（生产 `COOKIE_SECURE=true`） |
| 角色矩阵 RBAC | 网站 `permissions.ts` | ✅ 已有，扩展 techrep/viewer |
| 备份加密 AES-256-GCM | 网站 | ✅ 已有 |
| 设备通道 PGP 加密 | CIMS | ✅ 已有 |
| 双因素 2FA | CIMS TOTP | ✅ 已有 |
| 审计日志 | CIMS audit + 网站 | ✅ CIMS 原生；网站补操作审计 |
| 指令防重放（ts+token 验签） | 本章 1.2 | 🆕 新增（代理侧） |
| 远程控制会话级端口 + 令牌 | 本章 2 | 🆕 新增（代理侧） |
| HTTPS 强制 / 源站白名单 | 网站 outboundWhitelist 模式 | ✅ 可复用 |
| 限流 / 暴力破解防护 | 网站 + CIMS 登录 | ⚠️ 建议补（见 §5） |

## 4. 与 stelarith-website 联动（落地三条线）

### 4.1 SSO / 统一登录（线一）

- 集控面板作为网站的一个**同源模块**（新增 `/console` 路由，见 `ext/stelarith-website-sync/`），共享 `admin_token` Cookie。
- 未登录 → 网站 `/admin/login`；登录后按角色渲染面板菜单。
- 好处：一套账户、一套角色、一次登录，全站（CMS + 集控）通用。

### 4.2 内容源 → 设备（线二："网站驱动屏幕"）

- 网站 CMS 作为**校园公告 / 课表 / 通知的单一内容源**（已有文章/文档/设置管理能力）。
- 同步脚本 `sync-to-cims.mjs`：读取网站指定内容（如 `folder="校园公告"` 的文档、或 `settings.json` 里的课表快照），调用 **CIMS 真实资源写接口** `POST /account/{acct}/{type}/write?name=`（type∈ClassPlan/Policy/DefaultSettings…），设备经 Manifest 自动拉取生效。
- 这样"在网站上发一条公告"→ 全校/全班屏幕自动更新，真正实现网站与集控联动。

### 4.3 状态门户 / 嵌入（线三）

- 网站新增只读页面，聚合展示 CIMS 设备在线状态、当前公告（经 CIMS 只读接口或代理中转）。
- 电教委员在网站内即可"看到全校屏幕状态 + 一键进入集控面板"。
