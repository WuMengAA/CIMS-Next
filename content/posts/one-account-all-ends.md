这个生态里有好几个"入口"：网页主站、星集控管理端（Qt 桌面程序）、星集控被控端（教室一体机上的托盘程序）、云端点歌站。如果每个入口各做一套账号，用户要记四套密码，而运维要维护四份用户数据——不出三个月必然对不上。

所以做成了**一个账号进所有端**。

## 主站是授权服务器

结构上是标准的 OAuth2 授权码流程，主站扮演授权服务器（IdP），其他都是客户端：

```
用户在客户端点"登录"
   → 跳转到主站授权页
   → 主站确认身份（已登录直接进，未登录先登录）
   → 用户点"同意"
   → 主站发一次性授权码，跳回客户端
   → 客户端用授权码换访问令牌
   → 客户端用令牌取用户资料
```

客户端拿到的令牌就是主站的会话令牌。之后客户端调主站的接口，都带这个令牌——**权限判定仍然在各接口自己那侧做**。拿到令牌不等于拿到后台权限，这是两件事。

## 三种客户端，三种安全模型

难点在于三种客户端的安全约束完全不同，不能用同一套方案。

**Web 客户端（点歌站）**：标准 confidential client。有服务端、能存密钥，回拨地址是登记过的固定 https 地址。授权码 5 分钟过期、单次使用、绑定回拨地址。

**桌面端（星集控管理端）**：这是最麻烦的一类。它是装在用户机器上的程序，**任何藏在安装包里的密钥都能被反编译抠出来**。早期版本确实内置了一个默认密钥，等于"打包即附带登录权限"。

后来的做法是按 RFC 8252 把它当**公开客户端**：不设密钥，安全性靠三件事叠加——授权码必须用户在场同意才发、回拨只收本机 127.0.0.1 的临时端口、回拨地址和授权时完全一致。这样即使有人拿到授权码，也没有可用的回拨地址去兑换。

**被控端（教室一体机）**：更极端——它是无人值守的机器，连"用户在场同意"都做不到。做法是**首启动态注册**：设备启动时带设备指纹向主站注册，主站为它生成专属 client_id 和随机密钥。包里零密钥，反编译安装包什么都拿不到。之后每次开机用设备票（HMAC 签名、30 天有效、绑定指纹）续期。

## 为什么不让客户端直接碰密码

这是整个设计里最重要的一条：**密码从来不离开主站**。

客户端只拿到"这个人是谁"——用户 ID、昵称、头像、角色。拿不到密码，也拿不到主站的后台权限。好处很直接：

- 改密码只改一处，所有端立即生效；
- 撤一个人的权限只撤一处；
- 某个客户端被攻破，泄露的只是一个会话令牌，不是一批密码。

## 授权码为什么这么短命

5 分钟、单次使用、绑定回拨地址。三条都是必需的：

- 授权码在浏览器地址栏里可见，还可能留在历史记录和 referer 里，**它天生是暴露的**，所以必须短命；
- 单次使用保证截获的码只能用一次；
- 绑定回拨地址保证码不能被拿到别的域名去兑换。

## 踩过的坑

**坑一：藏在包里的默认密钥。** 桌面端最初内置 `dev-xingjikong-secret-change-me` 这种公开默认值。任何人反编译安装包都能以"星集控桌面端"身份走授权。改公开客户端才解决。

**坑二：env 兜底在运行时失效。** 客户端注册表从配置文件迁到数据库后，有一段时间"环境变量兜底"这条路径是断的——库里密钥为空时，即使 `.env` 配了也读不回来，表现为授权一律失败。原因是构造记录时漏带了一个字段。这类 bug 的特征是"配了等于没配"，最难排查。

**坑三：布局层的 canonical 抢戏。** 这个不算登录的坑，但是同一类错误——以为某处做了正确的事，实际上它把详情页的 canonical 全指向了首页。**默认值用错地方，比没有默认值更糟。**

## 现在的状态

三类客户端都在跑：点歌站用 Web 流程，管理端用公开客户端 + 本机回拨，被控端用动态注册 + 设备票。后台能看到全部客户端、每个客户端的启停状态、以及每次登录的来源。
