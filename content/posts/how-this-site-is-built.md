常有人问这个站用什么搭的。这篇把选型和理由一次说清，包括哪些是刻意做的取舍，以及代价是什么。

## 一句话版本

**SvelteKit 2 + Svelte 5（runes）+ adapter-node，内容走文件式存储，动态数据走 SQLite/PostgreSQL 双后端，单进程部署。**

## 为什么是 SvelteKit

三个理由，按重要性排：

1. **需要服务端渲染**。这个站有博客、文档、论坛、榜单——全是靠搜索引擎吃饭的内容。纯客户端渲染等于自断收录。SSR 不是可选项。
2. **同栈复用**。桌面端、云端服务都是 Node/TypeScript，网站侧不需要再引入一套语言和工具链。
3. **构建产物小、行为可预期**。adapter-node 产出一个 Node 服务，没有边缘运行时的怪癖。

## 数据分三层，各管各的

这是最容易讲错的地方，所以单独说。站上的数据**不是全塞一个地方**，而是按"怎么变"分成三层：

| 层 | 存什么 | 为什么 |
|---|---|---|
| Markdown 文件 | 文章、项目、文档、页面 | 人写的、改得少、要能直接 `cat` 看、要能进 git |
| JSON 文件 | 导航、设置、公告、友链、看板 | 配置类、量小、要能人工 review |
| SQLite / PostgreSQL | 用户、会话、评论、附件、班级数据、设备 | 并发写、要查询、要事务 |

文件式存储的代价是并发写入要自己处理；换来的是**备份等于复制目录、迁移等于换路径、出问题能直接读文件**。对单人运维的站，这个交换划得来。

第三层现在有双后端：开发与本机用 Node 内置的 `node:sqlite`（零第三方依赖，WAL 模式）；云端部署包切 PostgreSQL 17。两边跑同一套异步门面（`DbFacade`），方言差异收拢在翻译层里。切 PG 之前做过一轮全量对账：42 张表、2817 行、5 条复杂查询逐条比对，零差异——**迁移的成本花在验证上，不花在"希望它没问题"上**。要说清楚的风险：`node:sqlite` 是 Node 的实验 API，跨小版本可能变，所以 Node 版本锁死，升级前必须测数据层。

## SEO 是后来补的一课

早期每个页面自己写 `<svelte:head>`，结果参差不齐：有的页面连 description 都没有，全站没有一段结构化数据，文章甚至没有详情页（列表在链，点进去 404）。

后来做了三件事：

- **一个共享 SEO 组件**，所有页面统一出口。传标题和路径，canonical、OG、Twitter 卡片、结构化数据一次齐活。新增页面不会再漏。
- **清理了布局层的冲突标签**。布局原本给每个页面都输出指向首页的 canonical——这等于告诉搜索引擎"所有详情页都是首页的副本"，会把详情页踢出索引。而 Svelte 的 `svelte:head` 不做去重，两个标签会同时输出。
- **结构化数据**。首页声明 WebSite + Organization，文章和详情页声明 Article + BreadcrumbList——搜索结果里能带出作者、日期、站点名，而不是一行蓝字。

顺带一个反例：有几个"功能建设中"的占位页（追番、游戏、交互小说），一开始被误设为可收录。**收录空占位页是 thin content，是 SEO 的反面教材**，后来全部改成 noindex。

## 部署：单进程 + Docker 栈 + Cloudflare 边缘

本机仍然是一个 Node 进程 + 一个守护脚本（崩了自动拉起来），发布走原子发布：新版本构到旁路目录，校验通过后再切换，失败自动回滚。

云端多了两层，都不改应用形态：

- **Docker 栈**（`deploy/site/`）：网站 + PostgreSQL + nginx 一个 compose 起来，多阶段构建隔离产物，运行时数据全走挂卷，不烤进镜像。配套 30 分钟周期的备份（pg_dump + 打包，异地目标可插拔）。
- **Cloudflare Tunnel**：源站不开放任何入站端口，只出网连 CF，IP 彻底隐藏；TLS 由 CF 边缘终止，WAF 和缓存规则在边缘生效。国内访客的提速走 IP 优选（CloudflareST 选边缘 + hosts/路由器 DNS 指过去），免费档的极限也就到这里。

单实例的前提仍然成立：OAuth 授权码已挪出进程内存进库，但数据库单写者这条没变。上多实例之前，PG 连接池和授权码存储还得再各过一遍。

## 版本：双轨制

站点版本是两条线，各管各的（参考 acofork 的机制）：

- **站点版本（semver）**：`package.json` + changelog 管"发版"，当前 v1.0.0。后台发一条 changelog 就是一个版本。
- **内容版本（git commit）**：构建期把 HEAD 短 hash 打进产物，页脚实时显示"内容 8932abd"，访客端轮询 `/api/version`，发现 commit 变了底部出条"点击刷新体验"——网页版热更新，不自动刷（你在写的表单不该被刷新吃掉）。

## 主题：两套皮肤，一个开关

默认是经典皮肤（暖橙纸墨）；2026-10 上线的**终末地 BETA** 是独立的第二套皮肤，右上角切换器一键切，选择记在 localStorage，刷新不闪。两套皮肤共用同一套设计令牌的不同取值，不是两坨各写一遍的 CSS——切皮肤 = 切一组令牌。

## 什么没做

- **没有微服务**。单体在单人运维下是优势，不是债。
- **没有 CDN 前置动态内容**。静态资源可以走 CDN，但页面本身是 SSR，CF 边缘只做缓存/安全/隐藏 IP，不做全站加速的幻觉。
- **没有上 R2 图床**。需要绑卡订阅，本期本地卷过渡，接口留着（`BACKUP_OFFSITE_CMD`），绑了卡再接。

## 总结

这个站的架构原则只有一条：**让一个人能兜住**。备份是拷目录、部署是一条命令、出问题能直接读文件、数据层零第三方依赖。所有看起来"不够先进"的选择，都是拿先进性换可维护性——而可维护性是一个人运维时唯一不能妥协的东西。
