常有人问这个站用什么搭的。这篇把选型和理由一次说清，包括哪些是刻意做的取舍，以及代价是什么。

## 一句话版本

**SvelteKit 2 + Svelte 5（runes）+ adapter-node，内容走文件式存储，动态数据走 SQLite，单进程部署。**

## 为什么是 SvelteKit

三个理由，按重要性排：

1. **需要服务端渲染**。这个站有博客、文档、论坛、榜单——全是靠搜索引擎吃饭的内容。纯客户端渲染等于自断收录。SSR 不是可选项。
2. **同栈复用**。桌面端、云端服务都是 Node/TypeScript，网站侧不需要再引入一套语言和工具链。
3. **构建产物小、行为可预期**。adapter-node 产出一个 Node 服务，没有边缘运行时的怪癖。

## 数据分三层，各管各的

这是最容易讲错的地方，所以单独说。站上的数据**不是全塞一个地方**，而是按"怎么变"分成三层：

| 层 | 存什么 | 为什么 |
|---|---|---|
| Markdown 文件 | 文章、项目、文档、页面 | 人写的、改得少、要能直接 `cat` 看、要能进 git |
| JSON 文件 | 导航、设置、公告、友链、看板 | 配置类、量小、要能人工 review |
| SQLite | 用户、会话、评论、附件、班级数据、设备 | 并发写、要查询、要事务 |

文件式存储的代价是并发写入要自己处理；换来的是**备份等于复制目录、迁移等于换路径、出问题能直接读文件**。对单人运维的站，这个交换划得来。

SQLite 用的是 Node 内置的 `node:sqlite`（零第三方依赖），WAL 模式。这个选择的风险要说清楚：它是 Node 的实验 API，跨小版本可能变——所以 Node 版本是锁死的，升级前必须测数据层。

## SEO 是后来补的一课

早期每个页面自己写 `<svelte:head>`，结果参差不齐：有的页面连 description 都没有，全站没有一段结构化数据，文章甚至没有详情页（列表在链，点进去 404）。

后来做了三件事：

- **一个共享 SEO 组件**，所有页面统一出口。传标题和路径，canonical、OG、Twitter 卡片、结构化数据一次齐活。新增页面不会再漏。
- **清理了布局层的冲突标签**。布局原本给每个页面都输出指向首页的 canonical——这等于告诉搜索引擎"所有详情页都是首页的副本"，会把详情页踢出索引。而 Svelte 的 `svelte:head` 不做去重，两个标签会同时输出。
- **结构化数据**。首页声明 WebSite + Organization，文章和详情页声明 Article + BreadcrumbList——搜索结果里能带出作者、日期、站点名，而不是一行蓝字。

顺带一个反例：有幾個"功能建设中"的占位页（追番、游戏、交互小说），一开始被误设为可收录。**收录空占位页是 thin content，是 SEO 的反面教材**，后来全部改成 noindex。

## 部署：单进程，没有花活

没有 Docker，没有 PM2，没有 K8s。就是一个 Node 进程 + 一个守护脚本（崩了自动拉起来）。

这个选择的前提是**单实例**：SQLite 单写者、OAuth 授权码存在进程内存里，都要求"同时只有一个进程在跑"。如果哪天要上多实例，这两处必须先改——数据库换 PostgreSQL、授权码挪出内存。在那之前，单进程是最省心的形态。

发布走原子发布：新版本构到旁路目录，校验通过后再切换，失败自动回滚。目的是消灭"构建中恰好重启 → 连崩几分钟完全打不开"这个窗口。

## 什么没做

- **没有微服务**。单体在单人运维下是优势，不是债。
- **没有 CDN 前置动态内容**。静态资源可以走 CDN，但页面本身是 SSR，没必要。
- **没有上 PostgreSQL**。当前量级 SQLite 完全够，迁移是真实成本（几百处数据访问要从同步改异步），等真有需求再说。

## 总结

这个站的架构原则只有一条：**让一个人能兜住**。备份是拷目录、部署是一条命令、出问题能直接读文件、数据层零第三方依赖。所有看起来"不够先进"的选择，都是拿先进性换可维护性——而可维护性是一个人运维时唯一不能妥协的东西。
