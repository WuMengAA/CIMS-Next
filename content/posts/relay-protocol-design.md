做多人联机，很多人第一反应是 WebRTC、信令服务器、NAT 穿透全家桶。但星璃的"一起听 + 体素联机"先问了一个问题：**到底要同步什么？**

答案很窄——播放态、少量编辑、聊天。既然要同步的东西这么少，协议就可以极简，复杂方案带来的成本一个都不必付 [1]。

## 先定范围：联机只搬控制帧，不搬音频流

这是整套设计的地基。音频流**不经过联机通道**，每个客户端各自播放本地那份文件；联机只同步"该播哪首、播到几秒、是播还是停"。

这个取舍带来三个直接好处：带宽从"每人几百 kbps"降到"每秒几十字节"；没有音频中转的延迟与抖动问题；**断网不会让别人正在听的歌突然停**，只是不再同步。

> [!TIP]
> 把"联机"和"播放"解耦，是这套协议最关键的决策。代价是要求参与者本地都有同一份曲库——对一个本地播放器来说，这个前提本来就是成立的。

## 拓扑：星型而非 P2P 全连通

| 拓扑 | 状态一致性 | 冲突处理 | 实现成本 | 适用 |
|------|------------|----------|----------|------|
| P2P 全连通 | 差（N 份真相） | 需要共识/仲裁 | 高 | 实时对战 |
| **星型（房主中心）** | **好（唯一真相）** | **房主说了算** | **低** | 一起听、协同编辑 |

星璃选星型：一个房主维护房间真相（当前曲目、进度、播放态、场景编辑），客户端订阅并跟随。状态唯一、冲突少、逻辑简单——对于一个"有一个天然 DJ"的场景，这是显然的选择。

## 消息信封

所有通信走一个 JSON 信封 `NetMessage`：

```json
{ "t": 8, "f": "<fromId>", "to": "<peerId|null>", "p": { "...": "payload" } }
```

| 字段 | 含义 |
|------|------|
| `t` | 消息类型（`listenState=8`、`edit=5`、`chat=7`、`editSnapshot=12`…） |
| `f` | 来源 peerId，用于**自环过滤**（自己发的不回显给自己） |
| `to` | 有值 → 定向投递；`null` → 广播给同房其他成员 |
| `p` | 业务载荷，按 `t` 不同而异 |

信封保持极薄是刻意的：中转服务器不需要理解业务语义，只按 `to` 路由，否则每次加功能都要改服务端。

## 一起听：主机即 DJ

房主播放时周期性广播 `listenState`（曲目 + 进度 + 播放态）。客户端收到后本地执行 `_applyRemoteListen`，把进度和播放态对齐。

```dart
void _applyRemoteListen(ListenState s) {
  // 关键：用「发送时刻 + 已流逝时间」推算当前进度，而不是直接用收到的 position
  final elapsed = DateTime.now().millisecondsSinceEpoch - s.sentAt;
  final corrected = s.position + Duration(milliseconds: elapsed);

  // 漂移小于阈值就不纠正，避免频繁 seek 造成听感抖动
  final drift = (corrected - _player.position).abs();
  if (drift < const Duration(milliseconds: 300)) return;
  _player.seek(corrected);
}
```

> [!WARNING]
> **进度同步最容易做错的一点：直接把收到的 `position` 拿去 seek。** 消息在网络上要走一个 RTT，你收到的永远是"过去的进度"，每人会稳定慢半拍。必须带上**发送时刻**，客户端按 `发送时刻 + 已流逝时间` 推算。这一条不做，一起听就会永远差半秒，而且没人说得清为什么。

广播频率也是取舍：1 秒 1 次足够，切歌 / 暂停 / seek 时**立即**广播一次。频率调高只会徒增耗电与流量，不会更准。

## 跨网：薄薄一层中继

局域网用 UDP 发现（`LanDiscovery`）；跨公网加一个**协议复用的房间感知扇出器**（中转服务器 net-relay）：它不解析业务语义，只按 `to` 定向、否则广播，客户端协议原样透传。

正因为信封足够薄，这个中继可以写得非常短——它连"现在播的是哪首歌"都不需要知道。

## 五个真实踩过的坑

1. **自环没过滤**：早期没处理 `f` 字段，房主发出的消息又被中继广播回来，导致状态被自己覆盖、播放反复 seek。所有收到的消息**先判 `f == 自己的 id` 就丢弃**。
2. **过期状态覆盖新状态**：UDP 不可靠、乱序，一条迟到的旧 `listenState` 可能覆盖掉刚收到的新状态。给状态消息加**单调递增序列号**，收到比当前更小的就丢弃。
3. **房主断线导致客户端乱跳**：房主掉线后，客户端如果继续按最后的进度推进，会越走越偏。正确行为是**冻结在当前状态**并提示"房主已断开"，而不是自己往前跑。
4. **UDP 发现不稳定**：一次组播问询经常收不全。发现阶段要**重试 2~3 次并等满超时**，别只发一次就认为"局域网没别人"。
5. **重连风暴**：网络抖动时客户端疯狂重连，把中继打满。必须做**指数退避**（1s、2s、4s…上限 30s），并在恢复后重新拉一次完整快照，而不是靠增量补齐。

## 小结

| 决策 | 选择 | 理由 |
|------|------|------|
| 同步内容 | 只同步控制帧 | 带宽极低，断网不停歌 |
| 拓扑 | 星型房主 | 唯一真相，无冲突仲裁 |
| 信封 | 极薄 JSON | 中继无需理解业务 |
| 进度同步 | 带发送时刻推算 | 消除 RTT 造成的恒定偏差 |
| 重连 | 指数退避 + 拉快照 | 避免风暴与状态错乱 |

这套协议的全部复杂度，都花在**处理不可靠网络**上，而不是花在功能上。这大概是所有联机协议的共同点：功能你能想到，但让它"在不稳定的网络上也表现正常"，才是真正的工程量 [2]。
