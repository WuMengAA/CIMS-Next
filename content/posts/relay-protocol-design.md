做多人联机，很多人第一反应是 WebRTC、信令服务器、NAT 穿透全家桶。但星璃的"一起听 + 体素联机"先问了一个问题：**到底要同步什么？** 答案很窄——播放态、少量编辑、聊天。于是协议可以极简。

## 星型拓扑：房主即中心

不用 P2P 全连通，而是**星型**：一个房主（host），多个客户端（client）。房主维护房间真相（当前曲目、进度、播放态、场景编辑），客户端向房主订阅并跟随。好处是状态唯一、冲突少、逻辑简单。

## 消息信封

所有通信走一个 JSON 信封 `NetMessage`：

```json
{ "t": 8, "f": "<fromId>", "to": "<peerId|null>", "p": { "...": "payload" } }
```

- `t`：消息类型（`listenState=8` 一起听、`edit=5` 编辑、`chat=7` 聊天、`editSnapshot=12` 编辑快照……）
- `to` 存在 → 定向投递；为 `null` → 广播给同房其他成员
- `f`：来源，用于自环过滤（自己发的不会回显给自己）

## 一起听：主机即 DJ

房主播放时，周期性广播 `listenState`（曲目 + 进度 + 播放态）。客户端收到后本地执行 `_applyRemoteListen`：把进度对齐、把播放态对齐。**播放本身在各自设备发生**，联机只同步"该播哪、播到哪"。所以断网不会让别人的歌停，只是不再同步。

> [!TIP]
> 把"联机"和"播放"解耦，是这套协议最关键的取舍：联机只搬控制帧，不搬音频流。省掉了音频中转的带宽与延迟噩梦。

## 跨网：薄薄一层中继

局域网用 UDP 发现（`LanDiscovery`），跨公网加一个**协议复用的房间感知扇出器**（中转服务器）：它不解析业务语义，只按 `to` 定向、否则广播——客户端协议原样透传（详见「星璃音乐·中转服务器」项目）。
