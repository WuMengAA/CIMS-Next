"会思考的播放器"听起来像噱头，落地到星璃是具体的一件事：**本地歌单策展**。它不做云端推荐，不收集用户数据，而是在设备本地，用小模型根据你已有的曲库和听歌习惯，排出一版"此刻想听"的歌单。

## 为什么坚持本地

云端推荐的前提是把行为数据传上去。但对一款"本地优先"的播放器，这和内容留在硬盘上的理念直接冲突——如果歌声留在本地、听歌记录却要上传，那"本地"就只剩一半。

所以策展模型跑在本地：**输入是你自己的曲库元数据与播放行为，输出是一份排序建议，数据全程不出设备。**

## 特征从哪来：只用端上采得到的信号

没有云端画像，可用的就只有本地信号。我把它们分成三类：

| 类别 | 具体特征 | 来源 |
|------|----------|------|
| 曲目固有 | 流派、BPM、时长、能量、发行年份 | 刮削 + 本地音频分析 |
| 播放行为 | 完成率、跳过率、重复播放次数、最后播放时间 | 本地播放日志 |
| 上下文 | 时段、星期、是否在充电、当前是否在投屏 | 设备状态 |

**完成率和跳过率是最强的两个信号**：一首被反复跳过的歌，无论"猜你喜欢"算得多准都该降权；一首完整听完又立刻重播的歌，权重应该拉满。这两个信号完全本地可得，不需要任何外部数据。

> [!NOTE]
> 策展是"辅助"不是"替你决定"。模型给的是一版建议排序，你随时可以打乱、剔除、锁定。它的目标是减少"打开播放器却不知道听啥"的空白，而不是接管你的品味。

## 模型选型：为什么不用大模型

设备端推理有两套成熟底座可选：

- **TensorFlow Lite（现 LiteRT）**：把训练好的模型量化后跑在手机 / 桌面，体积小、延迟低，适合排序、分类这类任务 [1]
- **MediaPipe Tasks**：Google AI Edge 提供的跨平台任务 API，封装了模型加载与推理，能直接在 Flutter 侧集成 [2]

> [!WARNING]
> 我早期试过用**大模型**做策展，结论是**放弃**。三个原因：一是端上跑不动（哪怕量化后，延迟和资源占用对播放器这种常驻应用都太重）；二是收益不成正比——歌单排序本质是"给几十首候选打分"的简单任务，不需要语言理解能力；三是大模型容易输出不稳定的结果，而排序需要**可解释、可复现**。

小模型做这件事足够了。它不需要海量参数，要的是"快、稳、在端上跑得动"。

## 打分：一个刻意保持简单的函数

我没有用复杂的 Learning-to-Rank，而是保留了一个**可读、可调试**的线性加权。原因很实际：排序出问题时，我需要能一眼看出是哪一项把分数顶上去的。

```dart
double scoreTrack(Track t, CurationContext ctx) {
  // 各项都在 0~1，权重按场景切换
  final affinity = _affinity(t);          // 历史偏好（完成率/重复播放）
  final recency  = _recencyDecay(t);      // 距上次播放的衰减，避免总推同一批
  final fit      = _contextFit(t, ctx);   // 与当前场景的匹配度
  final fatigue  = _fatiguePenalty(t);    // 近期听腻的惩罚

  return 0.40 * affinity
       + 0.25 * fit
       + 0.20 * recency
       - 0.15 * fatigue;
}
```

`recency` 和 `fatigue` 这两项是我后来加的。第一版只有 `affinity` 和 `fit`，结果是**同一批高分歌反复出现**——用户听三次就腻了。加了衰减与惩罚项之后，"懂你"才没有变成"烦你"。

## 场景化才是落点

比起"猜你喜欢"，更有用的是"现在该听啥"。场景标签来自本地使用节律，不依赖任何外部信号：

| 场景 | 推断依据 | 权重倾向 |
|------|----------|----------|
| 深夜专注 | 时段 + 长时间连续播放 | 低饱和纯音乐、无人声、可叠白噪音 |
| 通勤 | 时段 + 移动网络/投屏状态 | 节奏明确、能量偏高 |
| 周末整理 | 周末 + 随机切歌频繁 | 熟悉曲目、高完成率 |
| 运动 | 设备传感器（可选，需授权） | BPM 与目标区间匹配 |

场景判断全部基于**本地可推断的信息**，并且**默认不申请任何敏感权限**——传感器这类需要授权的能力，不授权就退化为纯时段推断，功能不残废。

## 四个真实踩过的坑

1. **冷启动完全没信号**：新装用户零播放历史，模型无从下手。第一周退化为"按流派均匀采样 + 热门度兜底"，等积累到一定播放量再切模型排序。**冷启动策略必须单独设计，不能指望模型自己扛。**
2. **过度个性化导致信息茧房**：只推高 `affinity` 的歌，用户三个月听不到新东西。加 `recency` 衰减和一定比例的"探索位"（低affinity但高场景匹配）才缓解。
3. **算力与耗电**：端侧推理不能常驻跑。我把它限制为"打开播放器时算一次，结果缓存"，不在后台周期性重算。
4. **特征漂移**：曲库大更新（比如一次性导入几千首新歌）后，原有权重的分布会整体偏移。需要对新增部分重新归一化，否则新歌永远排不进来。

## 隐私边界

最后明确一下边界，这也是整件事的前提：

| 数据 | 去向 |
|------|------|
| 音频文件 | 留在本地，永不上传 |
| 播放/跳过/完成记录 | 留在本地，仅用于本地打分 |
| 曲库元数据 | 仅刮削时向外查询（可关闭） |
| 设备状态与时段 | 本地推断，不外发 |

**不上传、不建云端画像、不做跨设备同步。** 代价是推荐质量上限低于云端方案——这个交换我认了。隐私与懂你，不是二选一，但确实需要接受"没那么懂"这个上限。
