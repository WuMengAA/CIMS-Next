# 07 · 公网接入与容灾双实例

> 面向：把服务端放到公网、供多校/多班设备接入，并且要求「主机挂了不能停」的人。
> 前提（已确认）：**两台应用实例共享同一套 PostgreSQL + Redis**，公网入口**走 Cloudflare Tunnel**。

---

## 0. 三条结论先摆出来

1. **不需要公网 IP、不需要自己申请证书、不需要开放任何入站端口。**
   Tunnel 是由内网**主动出站**连到 Cloudflare 边缘的，源站这一侧只监听 `127.0.0.1`。
   证书由 Cloudflare 边缘提供（Universal SSL）。
2. **只有客户端 API（8096）需要域名。** 服务端的 `TenantMiddleware` 只挂在 `client_app` 上；
   管理 API（8097）走 `AccountContextMiddleware` 的路径参数，Admin API（8098）走会话令牌，
   **两者都不看 Host**。所以面板怎么接都行。
3. **容灾不需要「切换动作」。** 同一个 Tunnel 可以挂多个 cloudflared 连接器，
   Cloudflare 自动在它们之间分发；某个连接器断开，流量自动继续给另一个。
   加上两台共享同一套库，这就是**零切换、自动容灾的双活**。

---

## 1. 为什么 Host 头是这件事的核心

服务端用 `extract_slug_from_host()` 从 Host 里切出租户标识，**要求 Host 必须以 `.CIMS_BASE_DOMAIN` 结尾**。
而教室端插件在**全部 9 处 HTTP 请求**里都强制覆写 `Host = <Slug>.<BaseDomain>`，
与它实际连的地址无关。

推论：

| 结论 | 说明 |
|---|---|
| 连哪个地址与「是哪台租户」解耦 | 插件连 `https://<slug>.<base>`，Host 也是 `<slug>.<base>`，两者天然一致，最不容易出错 |
| 必须走**泛域名** | 每个租户一个子域名，靠 `*.基域` 一条规则覆盖，不用逐个加 |
| 反代/隧道**必须原样透传 Host** | 一旦被改写成 upstream 名或公网主机名，slug 解析为空 → **全站 403** |

> Cloudflare Tunnel 的 `httpHostHeader` 默认为空，即**原样转发客户端 Host** —— 正是我们要的行为。
> **不要**去设它。
>
> 如果你改用 Nginx/frp：Nginx 必须写 `proxy_set_header Host $http_host;`（不是 `$proxy_host`）。
> frp 用 **TCP 模式**最省心（原样透传，连 Host 都不用管）。

## 2. 目标架构

```
   教室端插件（多校 / 多班）
        │  HTTPS，HTTP Host 固定为 <slug>.<基域>
        ▼
   ┌──────────────────────────────────────────┐
   │ Cloudflare 边缘                            │
   │   DNS: *.cims.example.com                 │
   │        CNAME → <隧道ID>.cfargotunnel.com   │
   │   TLS: Universal SSL（覆盖一级泛域名）      │
   └──────────────────────────────────────────┘
        │  同一个 Tunnel，自动在多个连接器间分发
        ├─────────────────────┐
        ▼                     ▼
   cloudflared (A)        cloudflared (B)
        │                     │
        ▼                     ▼
   CIMS 实例 A            CIMS 实例 B
   :8096 :8097 :8098      :8096 :8097 :8098
        └─────────┬───────────┘
                  ▼
     ⚠️ PostgreSQL + Redis
        （**必须放在第三台机器**，见第 6 节）
```

**关键认识：A 和 B 是「同一具身体的两副手脚」，不是两套系统。**
它们共享数据库与 Redis，所以课表版本号、命令队列、登录令牌天然一致 ——
客户端打到哪一台，看到的状态都相同。

---

## 3. 教室端 / 部署包要改的

只改 `config\deployment.json` 三个字段：

| 字段 | 内网部署（原值） | 公网部署（新值） |
|---|---|---|
| `ServerBase` | `http://10.0.0.10:8096` | `https://demo-class.cims.example.com` |
| `BaseDomain` | `localhost` | `cims.example.com` |
| `Slug` | `demo-class` | `demo-class`（不变） |

> **建议把 `ServerBase` 写成租户自己的子域名**（`https://<slug>.<基域>`），
> 这样插件连接的目标与它覆写的 Host 完全一致，SNI 与 Host 不再打架。
> 写成 `https://cims.example.com` 也能用（泛域名会把 Host 路由过去），但多一层心智负担。

`ServerPanel` 填面板的公网地址，例如 `https://panel.example.com/admin/console`。
面板**不需要**租户子域名。

## 4. Cloudflare 侧配置

### 4.1 准备

- 一个域名，把 `cims.example.com` 作为**独立 zone** 加进 Cloudflare
  （这样 `*.cims.example.com` 是它的一级泛域名，能被免费版 Universal SSL 覆盖）。
- 创建隧道，拿到隧道 ID 与凭据文件：

```bash
cloudflared tunnel login
cloudflared tunnel create cims
# 记下输出的 Tunnel ID，凭据默认落在 ~/.cloudflared/<TunnelID>.json
```

### 4.2 DNS（两条记录）

| 类型 | 名称 | 内容 | 代理 |
|---|---|---|---|
| CNAME | `*.cims.example.com` | `<隧道ID>.cfargotunnel.com` | 已代理（橙云） |
| CNAME | `panel.example.com` | `<隧道ID>.cfargotunnel.com` | 已代理（橙云） |

> 面板刻意放在**泛域名之外**，避免和某个叫 `console` 的租户撞车。

### 4.3 连接器配置（A、B 两台都要放同一份）

`~/.cloudflared/config.yml`：

```yaml
tunnel: <隧道ID>
credentials-file: /etc/cloudflared/<隧道ID>.json

ingress:
  # 面板：放在泛域名规则**之前**，否则会被泛域名先匹配走
  - hostname: panel.example.com
    service: http://127.0.0.1:8090

  # 客户端 API：泛域名覆盖全部租户
  # 注意：不要设置 originRequest.httpHostHeader —— 默认原样透传客户端 Host，
  #       这正是多租户识别所依赖的行为。
  - hostname: "*.cims.example.com"
    service: http://127.0.0.1:8096

  # 兜底（必需）
  - service: http_status:404
```

装成系统服务，避免重启后掉线：

```bash
cloudflared service install
systemctl enable --now cloudflared
systemctl status cloudflared
```

### 4.4 管理端口绝不上隧道

`ingress` 里**只出现 8096 与 8090**。8097 / 8098 / 8100 **一律不配**，
它们只应该被本机访问。

## 5. CIMS 侧配置（A、B 两台都要）

`.env` 两处必须改：

```ini
# 必须是公网那个基域，否则 Host 解析不出租户
CIMS_BASE_DOMAIN=cims.example.com

# ★ 公网部署的关键项。cloudflared 在本机，所以对端恒为 127.0.0.1。
#   不配这一项，限流中间件会把「全网所有设备」看成同一个 IP。
CIMS_TRUSTED_PROXIES=127.0.0.1
```

### 为什么 `CIMS_TRUSTED_PROXIES` 是必须的

限流中间件 `CCProtectMiddleware` 的规则是：**同一 IP 在 60 秒内出现 ≥5 次 ≥400 响应，就封该 IP 60 秒**。

挂上隧道之后，所有公网请求在服务端眼里都来自 `127.0.0.1`。不配这个变量，后果是：

> 任意一个人（哪怕只是个扫描器）打出 5 个 404，**全网所有教室设备一起被封 60 秒** ——
> 表现为集体收不到广播、课表停更、面板全部离线。排查时会非常困惑，因为现象是"大家一起坏"。

配上之后，服务端会按 `CF-Connecting-IP`（Cloudflare 设置的权威头，客户端伪造不了）
取真实客户端 IP，**每台设备各算各的**。

> 实现上只在对端落在 `CIMS_TRUSTED_PROXIES` 内时才采信代理头。
> 这一点不能省：若无条件采信 `X-Forwarded-For`，攻击者每次换一个假 XFF 就能让限流彻底失效。
>
> 启动日志里会打印一行 `客户端 IP 判定：可信代理 = ...`，**上公网前请确认这行不是"未配置"**。

### 两台必须保持一致的清单

| 项 | 为什么 |
|---|---|
| `cims_server.key`（GPG 密钥） | gRPC 会话管理器用它签名/校验。两台不一致 → 设备在 A 上建立的会话拿到 B 上不认，表现为**随机掉线** |
| `.env` 全文 | 基域、可信代理、端口、同步密钥必须一致 |
| `.cims/config.json` 的 `DATABASE_URL` | 必须指向**同一个**库 |
| 代码版本 | 建议完全同版本，避免两侧行为不一致 |
| Tunnel 凭据文件 | 同一个隧道 ID，两个连接器 |

## 6. ⚠️ 这套容灾成不成立，取决于数据库放在哪

**如果 PostgreSQL / Redis 就跑在实例 A 上，那么「A 挂了切 B」是假容灾** ——
A 一挂，库也没了，B 连不上库同样服务不了。

所以：

| 方案 | 说明 |
|---|---|
| **库放第三台机器（推荐）** | A、B 各自连它。库本身成了单点，但至少应用实例可以随便挂 |
| **用云数据库（RDS）** | 托管备份/主从，最省心，代价是要钱 |
| 库放 A、B 只做冷备 | 只能防"应用进程崩"，防不了"整机断电"。要接受这个前提 |

Redis 同理。不过 Redis 里主要是登录令牌，**坏了影响是"需要重新登录"，不是数据丢失** ——
所以 Redis 优先级可以低于 PostgreSQL。

---

## 7. 双活下需要注意的三件事

因为 Cloudflare 会把请求轮流分给 A、B，这实际上是**双活**而非主备。共享库让它变得安全，
但有三点要清楚：

1. **启动时的建表竞态**：两台同时启动，`_reconcile_tenant_schemas()` 会并发建表。
   代码里对失败是 catch + warning 跳过，**不会导致启动失败**，但日志会有噪音。
   做法：让 B 比 A 晚启动 30 秒。
2. **限流计数各算各的**：`CCProtectMiddleware` 的计数在进程内存里，两台不共享。
   影响很小（阈值各自生效），但要知道"封禁不是全局的"。
3. **gRPC（8100）没走隧道**：设备侧走的是 HTTP 轮询，不受影响。
   如果后续有组件依赖固定地址连 gRPC，它只会打到其中一台。

## 8. 安全清单

| 项 | 要求 |
|---|---|
| 对外暴露 | **只有** 8096（客户端 API）与 8090（面板） |
| 8097 / 8098 / 8100 | 只监听本机 / 内网，**绝不配到隧道上** |
| 面板加一层 | 建议用 **Cloudflare Access（Zero Trust）** 保护 `panel.example.com` —— 面板本来就有登录，再套一层边缘认证，攻击面立刻小一大截 |
| 限流 | 确认 `CIMS_TRUSTED_PROXIES` 已配（见第 5 节） |
| 超级管理员密钥 | `CIMS_ADMIN_SECRET` 必须换掉默认值 |
| 跨系统同步密钥 | `CIMS_SYNC_KEY` 属于机密，别进版本库 |
| 后台登录保护 | 建议给面板管理账号开 TOTP 两步验证 |

## 9. 验证步骤（每条都要亲手跑）

按顺序做完，能覆盖 95% 的问题。

**§9.1 隧道通不通（在任一台服务器上）**

```bash
# 本地直连客户端 API：
#   注意必须带 Host，不带就是 403（这是设计如此，不是故障）
curl -i -H "Host: demo-class.cims.example.com" http://127.0.0.1:8096/

# 期望：200
```

**§9.2 公网通不通（在你自己的电脑上，不在服务器上）**

```bash
# 1) 不带租户的子域名 —— 拿不到 slug，应该 403
curl -i https://cims.example.com/
# 期望：403  code=100403 未识别出租户

# 2) 带租户的子域名 —— 应该 200
curl -i https://demo-class.cims.example.com/
# 期望：200

# 3) Manifest 接口（这才是插件真正要的）
curl -i https://demo-class.cims.example.com/api/v1/client/manifest
# 期望：200，且返回 7 个资源源
```

> 第 1 条返回 403 是**正确的**，别去"修"它。

**§9.3 容灾是不是真的（关键一步）**

```bash
# 记录当前返回，然后去 A 上把服务停掉
curl -i https://demo-class.cims.example.com/api/v1/client/manifest

# A 上：
systemctl stop cloudflared     # 只停隧道连接器
# 再测：应当仍然 200（说明流量切到 B 的连接器了）
curl -i https://demo-class.cims.example.com/api/v1/client/manifest

# 再把 A 的 CIMS 也停掉，重测：应当仍然 200
# 最后把两台都停掉，应当很快恢复成 502/超时 —— 这才说明测试有效
```

**§9.4 限流认不认得真实 IP**

```bash
# 故意制造 6 次 404（在同一个出口 IP 下）
for i in 1 2 3 4 5 6; do curl -s -o /dev/null -w "%{http_code} " \
  https://demo-class.cims.example.com/api/v1/client/nope; done

# 期望：前 5 次 404，第 6 次起 429（说明按真实 IP 计数生效了）
# 然后从**另一个网络**（手机热点）访问，应当仍是 200 —— 证明没有被连坐
```

如果从手机热点访问也被 429，说明 `CIMS_TRUSTED_PROXIES` 没配或配错了。

**§9.5 启动日志**

```bash
grep "客户端 IP 判定" <日志文件>
# 期望：可信代理 = 127.0.0.1/32（多租户基域 = cims.example.com）
```

## 10. 回退到单机

公网化和容灾都是**加法**，回退很轻：

1. 教室端 `deployment.json` 的 `ServerBase` 改回内网地址、`BaseDomain` 改回 `localhost`，
   重跑 `deploy.ps1`（或 `4-回滚.cmd -RestoreSyncOnly`）。
2. B 上的 cloudflared 停掉即可（A 上的隧道会独占流量）。
3. `CIMS_BASE_DOMAIN` 改回 `localhost`；`CIMS_TRUSTED_PROXIES` 可留可清空
   （直连时对端就是真实 IP，配了也不影响）。

> 注意：`CIMS_BASE_DOMAIN` 一改，**所有教室端必须同步改**，否则 Host 与基域对不上，
> 全部 403。这一条要么不改，要么一次改完。

---

## 11. 一句话总结

**泛域名一条规则解决多租户，隧道解决公网与证书，同隧道多连接器解决容灾，共享库解决一致性。**
真正需要你盯死的只有两件事：**数据库不能和主实例同机**，以及 **`CIMS_TRUSTED_PROXIES` 必须配**。
